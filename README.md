## نظرة عامة

**MowxBack** تطبيق محلي بسيط لإدارة دفتر يومي لمصنع أو منشأة صغيرة. يركز على تسجيل ومراجعة ثلاثة أنواع من البيانات:

1. **أرباح الأصناف:** تسجيل حركة ربح واحدة تحتوي صنفاً واحداً أو عدة أصناف، مع الكمية والربح لكل سطر.
2. **المصروفات:** إضافة المصروفات وتعديلها وحذفها ومراجعتها ضمن التقارير.
3. **سحبيات العمال:** تسجيل سحبيات العمال وعرضها ضمن التفاصيل وإجمالي المصروفات.

يهدف المشروع إلى إبقاء البيانات على جهاز المستخدم في قاعدة SQLite محلية، دون الاعتماد على خادم سحابي أو اتصال إنترنت أثناء الاستخدام اليومي.

> **حالة المشروع:** تم ربط الواجهة بطبقة SQLite عبر Electron، واجتازت اختبارات الحسابات وقاعدة البيانات وRepository وعقد IPC في بيئة التطوير. لم يثبت بعد تشغيل التطبيق وبناء مثبت Windows فعلياً؛ يجب اعتبار هذا المستودع نسخة تطوير قيد التحقق على Windows، لا إصداراً إنتاجياً معتمداً.

## النطاق الوظيفي

### يشمله المشروع

- سجل أرباح الأصناف مع دعم عدة أسطر في الحركة الواحدة.
- تسجيل المصروفات.
- تسجيل سحبيات العمال.
- إدارة قوائم الأصناف والعمال وتصنيفات المصروفات.
- تقارير حسب اليوم والفترة وتجميعات الأرباح والمصروفات.
- سجل تدقيق للتغييرات.
- اختيار مجلد قاعدة البيانات محلياً.
- نسخ احتياطي لقاعدة SQLite واستعادتها ونقلها.
- استيراد بيانات JSON من النسخة القديمة وتصدير نسخة JSON.
- دعم العملات SAR وJOD وAED وKWD وUSD وEGP وعملة مخصصة.

### خارج النطاق

هذا المشروع ليس نظام ERP أو نظام محاسبة متكاملاً. لا يتضمن إدارة المبيعات أو المشتريات أو المخزون أو العملاء والموردين أو الرواتب أو الحسابات البنكية أو المزامنة السحابية أو تعدد المستخدمين.

## صور وبنية النظام

لا يحتوي الأرشيف الحالي على صور واجهة مخصصة للعرض في README. يتكون التطبيق من واجهة HTML/CSS/JavaScript عربية، وطبقة Electron، وقاعدة SQLite محلية.

```text
Renderer (واجهة التطبيق)
        │
        ▼
js/storage.js + js/backup.js
        │  واجهة مسماة ومحدودة
        ▼
Electron Preload (contextBridge)
        │  IPC
        ▼
Electron Main Process
        │
        ▼
Repository + SQLite (better-sqlite3)
        │
        ├── المعاملات المالية
        ├── القوائم المرجعية
        ├── سجل التدقيق
        └── إعدادات التطبيق والترحيلات
```

### هيكل المجلدات

| المسار | المسؤولية |
|---|---|
| `index.html` | نقطة دخول الواجهة وسياسة أمان المحتوى المحلية. |
| `css/` | التنسيق والأصول والخطوط المحلية. |
| `js/app.js` | الصفحات والنماذج والعرض والتفاعل. |
| `js/storage.js` | وسيط عمليات البيانات من Renderer إلى Preload. |
| `js/backup.js` | عمليات النسخ والاستعادة والنقل والاستيراد والتصدير عبر الواجهة المحددة. |
| `electron/main.js` | إنشاء نافذة التطبيق، فتح القاعدة، تنفيذ IPC، العمليات والتقارير. |
| `electron/preload.js` | واجهة آمنة محدودة عبر `contextBridge`. |
| `src/database/` | فتح القاعدة، Repository، الحسابات، دورة حياة القاعدة، واستيراد JSON القديم. |
| `database/schema.sql` | لقطة كاملة قابلة للقراءة من مخطط SQLite. |
| `database/migrations/` | ملفات ترحيل المخطط. |
| `database/tests/` | اختبارات الحسابات وSQLite وRepository وعقد IPC. |
| `docs/` | وثائق التصميم والتدقيق والتكامل والاختبار وWindows. |
| `reference/original-source/` | نسخة مرجعية من ملفات المصدر الأصلية للمقارنة. |
| `.github/workflows/` | إجراءات GitHub Actions لبناء Windows x64. |

## المتطلبات

### لتطوير التطبيق

- Windows 10 أو Windows 11، معمارية x64.
- Node.js 24.
- npm المتوافق مع إصدار Node المثبت.
- اتصال إنترنت عند تنزيل التبعيات أول مرة.

### لتشغيل النسخة المثبتة

بعد إنشاء المثبت وتثبيت التطبيق، صُمم التشغيل اليومي ليكون محلياً ولا يعتمد على اتصال إنترنت. يجب التحقق من ذلك عملياً على جهاز Windows قبل اعتماد الإصدار.

## البدء والتشغيل على Windows

افتح PowerShell داخل مجلد المشروع، ثم نفّذ:

```powershell
npm ci
npm run rebuild:native
npm test
npm start
```

ملاحظات:

- `npm ci` يتطلب وجود `package-lock.json` مطابق لـ`package.json`. الحزمة المصدرية الحالية لا تتضمن ملف القفل؛ أنشئه مرة واحدة في بيئة Node/npm مناسبة ثم أدرجه في المستودع قبل الاعتماد على `npm ci`.
- `better-sqlite3` مكوّن Native؛ يجب إعادة بنائه لنسخة Electron المستهدفة قبل تشغيل/تغليف التطبيق.
- لا تفتح `index.html` مباشرة في المتصفح لتشغيل قاعدة البيانات. عمليات التخزين تعتمد على `window.mowx` التي يوفرها Electron Preload. خادم HTTP بسيط يعرض الواجهة فقط ولا يشغّل قاعدة SQLite.

## الاختبارات

شغّل كل مجموعات الاختبار باستخدام:

```powershell
npm test
```

تتضمن الحزمة:

| الأمر | التغطية |
|---|---|
| `npm run test:money` | تحويل المبالغ والكميات إلى تمثيل صحيح لتجنب أخطاء الفاصلة العائمة. |
| `npm run test:sqlite` | المخطط والقيود والعلاقات والمعاملات والتقارير والحذف المنطقي. |
| `npm run test:repository` | منطق Repository والاستيراد والتصدير وسجل التدقيق وإعادة فتح قاعدة ملفية. |
| `npm run test:bridge` | تطابق قنوات IPC وواجهات Preload وفحص عدم وجود مسار LocalStorage تشغيلي. |

### آخر نتيجة اختبار أبلغ عنها المستخدم

تم تنفيذ `npm test` في Termux بتاريخ 23 نوفمبر 2026، وكانت النتيجة:

- الحسابات المالية: **12 assertions ناجحة**.
- اختبارات SQLite: **15 اختباراً ناجحاً**.
- Repository/import: **50 assertions ناجحة**، مع اختبار تصدير سجل التدقيق وإغلاق/إعادة فتح ملف القاعدة.
- IPC bridge: **27 قناة و27 دالة وسيطة تم التحقق منها**.

هذه اختبارات منطق وبيانات وعقد اتصال. لا تثبت بمفردها أن Electron أو وحدة `better-sqlite3` تعمل على Windows، ولا أنها تثبت سلامة كل التفاعلات البصرية end-to-end.

للتفاصيل والقيود، راجع [`docs/test-plan.md`](docs/test-plan.md) و[`docs/phase-2-integration-report-ar.md`](docs/phase-2-integration-report-ar.md).

## بناء مثبت Windows (EXE)

يستخدم المشروع GitHub Actions لبناء مثبت NSIS x64 على Windows Runner.

1. ارفع المشروع إلى GitHub على الفرع `main`.
2. افتح تبويب **Actions**.
3. اختر **Build MowxBack for Windows**.
4. اضغط **Run workflow**.
5. بعد نجاح التشغيل، افتح سجل Workflow ثم نزّل Artifact باسم `MowxBack-Windows-x64`.
6. اختبر ملف EXE على Windows قبل توزيعه.

يمكن تشغيل Workflow تلقائياً عند دفع تغييرات ضمن المسارات المعرفة في ملف workflow، أو يدوياً باستخدام `workflow_dispatch`.

> ملاحظة تقنية: ملف Workflow في هذه الحزمة يستخدم حالياً `npm install`. يفضل بعد توفير `package-lock.json` موثوق تحديثه إلى `npm ci` لضمان تثبيت حتمي. لا تدّعِ نجاح البناء قبل رؤية تشغيل أخضر فعلي ووجود ملف EXE في Artifact.

## قاعدة البيانات وحماية البيانات

- تستخدم قاعدة SQLite محلية، ويديرها Electron Main Process عبر `better-sqlite3`.
- لا تصل الواجهة مباشرة إلى ملف DB ولا تتلقى واجهة `fs` أو `ipcRenderer` عامة.
- تُنفذ العمليات متعددة الخطوات داخل Transactions.
- تستخدم العلاقات والقيود وعمليات الحذف المنطقي للحفاظ على السجلات التاريخية.
- يسجل التطبيق التغييرات في `audit_log`.
- تُخزّن المبالغ والكميات كأعداد صحيحة scaled integers بدلاً من الاعتماد على الحسابات العائمة.
- إعدادات مسار القاعدة محفوظة خارج مجلد التثبيت، ضمن مساحة بيانات التطبيق للمستخدم.
- لا يُنشئ التطبيق قاعدة بديلة بصمت عند تعذر فتح قاعدة سابقة؛ يتطلب ذلك معالجة واضحة من المستخدم.

راجع [`docs/database-design.md`](docs/database-design.md) و[`docs/database-erd.md`](docs/database-erd.md) و[`database/README.md`](database/README.md).

## بيانات النسخة القديمة

إذا كانت لديك بيانات في الإصدار القديم، صدّر ملف JSON من النسخة القديمة أولاً، واحتفظ بنسخة أصلية آمنة. استخدم وظيفة استيراد JSON في التطبيق الحالي، ثم تحقق من عدد الحركات والسطور والمجاميع وسجل التغييرات قبل الاعتماد على البيانات المستوردة.

لا يحتوي هذا المستودع على بيانات المصنع الفعلية أو ملف JSON شخصي. لا ترفع قواعد بيانات المستخدمين أو ملفات النسخ الاحتياطية أو بيانات العملاء/الموظفين إلى مستودع عام.

## المساهمة والتطوير

قبل تقديم أي تعديل:

1. حافظ على نطاق التطبيق كدفتر أرباح ومصروفات وسحبيات.
2. لا تغيّر شكل الواجهة أو ترتيبها أو ألوانها أو RTL إلا عند وجود طلب صريح.
3. لا تعدّل Migration سبق تطبيقها؛ أضف Migration جديدة ورقمها تالياً.
4. أضف اختبارات لكل تغيير في الحسابات أو التخزين أو IPC.
5. لا تضف مفاتيح أو أسرار أو قواعد بيانات فعلية إلى Git.
6. لا تعتبر الاختبارات البنيوية بديلاً عن اختبار Windows الفعلي.
