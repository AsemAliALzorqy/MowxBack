# تصميم قاعدة بيانات MowxBack — SQLite v1

## 1. قرار التصميم

تم اختيار **جداول معاملات منفصلة ومترابطة** بدلاً من جدول حركة موحد متعدد الأنواع:

- `profit_transactions` رأس حركة أرباح واحد.
- `profit_lines` تفاصيل الأصناف داخل الحركة.
- `expenses` للمصروفات.
- `withdrawals` لسحبيات العمال.
- `items`, `workers`, `expense_categories` لقوائم الإدارة.
- `name_suggestions` لذاكرة الأسماء الحرة.

يعرض View موحد (`v_all_transactions`) العمليات للدفتر والتقارير، دون أن يفرض جدولاً عاماً يحتاج أعمدة كثيرة فارغة أو علاقات polymorphic غير محمية بمفاتيح خارجية. هذا يتبع الواجهة الحالية: حركة الربح المجمعة كيان أب مستقل، أما المصروف والسحبية فكل منهما عملية مستقلة.

لا يوجد جدول صندوق أو حسابات أو مبيعات أو مخزون أو رواتب أو قيود محاسبية عامة.

## 2. سياسة الأرقام والتواريخ

### المبالغ

لا تخزن المبالغ كـ `REAL` ولا كنصوص منسقة. تستخدم القاعدة عمود `INTEGER` باسم `amount_milli` يمثل 1/1000 من وحدة العملة:

- 12.345 من العملة تخزن `12345`.
- 12.34 تخزن `12340`.
- SAR/AED/USD/EGP: دقة عرض/إدخال افتراضية منزلتان.
- JOD/KWD: ثلاث منازل.
- العملة المخصصة: منزلتان افتراضياً لأن الواجهة الحالية لا تتيح تحديد دقة مخصصة.

تُخزن جميع العملات بالمقياس الداخلي نفسه؛ تغيير العملة يغيّر الرمز ودقة العرض فقط، ولا يغيّر القيمة الرقمية. اختيار دقة 3 داخلياً يسمح بحفظ قيم JOD/KWD دون تقريب، وفي عملات الدقتين تمثل قيمة كل مبلغ مضاعفاً لـ 10 من `amount_milli`.

قبل الإدخال يجب تحويل النص العشري إلى Integer بطريقة نصية/BigInt مع رفض تجاوز عدد المنازل المسموح، وليس عبر `Math.round(float * 1000)`.

### الكمية

تقبل الواجهة `step="any"` والكمية موجبة. لتجنب تخزين كميات عائمة، تخزن في `quantity_micros` كمليون جزء من وحدة الكمية. حد الدقة المقترح 6 منازل، ويجب رفض القيمة ذات دقة أعلى بدلاً من تقريبها بصمت.

### التاريخ

- تاريخ العملية: `YYYY-MM-DD` كنص موحد؛ يستخدم لتصفية اليوم والشهر والفترة.
- أوقات الإنشاء والتحديث والتدقيق: UTC ISO 8601 مثل `2026-11-23T18:00:00.000Z`.
- تحقق JavaScript من صحة تاريخ التقويم فعلياً؛ قيد SQLite يتحقق من شكل التاريخ وصلاحيته الأساسية.

## 3. الجداول

### 3.1 `profit_transactions`

| العمود | النوع | القيد/الغرض |
|---|---|---|
| `id` | TEXT | Primary Key؛ يحافظ على معرف الحركة القديم |
| `tx_date` | TEXT | تاريخ الحركة `YYYY-MM-DD`، CHECK |
| `created_at` | TEXT | UTC وقت الإنشاء |
| `updated_at` | TEXT | UTC آخر تعديل |
| `deleted_at` | TEXT NULL | حذف منطقي اختياري لرأس الحركة |

لا نخزن مجموع الربح والكمية المكرر في الرأس؛ يتم اشتقاقهما من السطور الفعالة في `v_profit_transaction_totals`. يمنع هذا اختلاف الإجمالي المخزن عن مجموع السطور بعد تعديل أو حذف صنف. الحركة التي لا يبقى لها سطر فعال تختفي من View، مع بقاء الرأس والسطور للتاريخ والتدقيق.

### 3.2 `profit_lines`

| العمود | النوع | القيد/الغرض |
|---|---|---|
| `id` | TEXT | Primary Key؛ معرف السطر |
| `transaction_id` | TEXT | FK إلى `profit_transactions.id`، `ON DELETE RESTRICT` |
| `item_id` | TEXT NULL | FK اختياري إلى `items.id`، ليس شرطاً للإدخال الحر |
| `legacy_ref_id` | TEXT NULL | يحفظ refId القديم حتى عند عدم وجود عنصر مطابق |
| `item_name` | TEXT | اسم الصنف الحر المخزن على السطر |
| `quantity_micros` | INTEGER | كمية موجبة مضروبة في 1,000,000 |
| `amount_milli` | INTEGER | ربح السطر موجب مضروب في 1,000 |
| `notes` | TEXT | ملاحظات اختيارية |
| `created_at`, `updated_at` | TEXT | وقتا الإنشاء والتحديث |
| `deleted_at` | TEXT NULL | حذف منطقي للسطر |

حركة واحدة يمكن أن تحتوي أي عدد من السطور. كل سطر يعدّل ويحذف منفرداً. عند تغير الاسم الحر، يُفصل المرجع الإداري الاختياري القديم إذا لم يعد الاسم يمثل العنصر نفسه.

### 3.3 `expenses`

- `id` معرف العملية القديم.
- `tx_date` تاريخ.
- `category_id` مفتاح أجنبي إلى `expense_categories`.
- `category_name_snapshot` اسم التصنيف وقت تسجيل المصروف.
- `amount_milli` مبلغ موجب.
- `description` الوصف كما في النموذج.
- `notes` ملاحظات.
- `created_at`, `updated_at`, `deleted_at`.

حفظ `category_name_snapshot` يمنع تغيير اسم الإدارة من تعديل السجل التاريخي الذي سبق إدخاله. أثناء إنشاء مصروف جديد يجب اختيار تصنيف نشط؛ عند تعديل مصروف قديم يظل تصنيفه الحالي قابلاً للاحتفاظ حتى إن أوقف.

### 3.4 `withdrawals`

- `id` معرف السحبية.
- `tx_date`.
- `worker_id` FK إلى `workers`.
- `worker_name_snapshot` اسم العامل وقت السحب.
- `amount_milli` مبلغ موجب.
- `notes`، وحقول الوقت والحذف المنطقي.

السحبيات لا تُنسخ إلى جدول المصروفات. `v_all_transactions` يعرضها بنوع `withdrawal`، و`v_daily_totals` يجمع `expense + withdrawal` مرة واحدة.

### 3.5 جداول الإدارة: `items`, `workers`, `expense_categories`

لكل جدول: `id TEXT PRIMARY KEY`, `name TEXT`, `is_active INTEGER CHECK 0/1`, `created_at`, `updated_at`, `deleted_at`.

- لا يستخدم `items` كمخزون أو شرط لإدخال الربح.
- لا يحتوي `workers` على راتب أو مستحقات.
- لا يحذف التصنيف/العامل/SKU مادياً عند الإيقاف؛ تبقى روابط العمليات سليمة.
- أضيفت التصنيفات التشغيلية الافتراضية: الطعام، المحروقات، الصيانة والأعطال. لا تزرع القاعدة أي عمليات مالية أو عمال أو أصناف تجريبية.

### 3.6 `name_suggestions`

| العمود | النوع | الوصف |
|---|---|---|
| `id` | INTEGER PK | معرف داخلي |
| `normalized_name` | TEXT UNIQUE | مفتاح التطبيع المستخدم للمطابقة ومنع التكرار |
| `display_name` | TEXT | الاسم الذي يظهر للمستخدم |
| `first_used_at`, `last_used_at` | TEXT | أول وآخر استعمال |
| `use_count` | INTEGER | عدد مرات الحفظ/الاستعمال |

الجدول مستقل تماماً عن `items`. عند نجاح حفظ حركة أرباح أو تعديل اسم سطر فقط يُضاف الاسم أو يحدّث استعماله. لا تُحذف اقتراحات الاسم عند حذف حركة أو سطر. يبحث التطبيق من حرفين ويعرض المطابقات التي تبدأ أولاً ثم التي تحتوي النص، بحد 8 كما في الواجهة الحالية.

التطبيع المطلوب يطابق الكود الحالي: trim وتوحيد المسافات، إزالة التشكيل والتطويل، توحيد أشكال الألف، ى إلى ي، ة إلى ه، وتحويل lowercase. SQLite لا يعيد تنفيذ قواعد Unicode العربية وحده؛ لذلك `normalized_name` يحسب في طبقة JavaScript ويخزن.

### 3.7 `audit_log`

| العمود | النوع | الوصف |
|---|---|---|
| `id` | TEXT PK | معرف حدث التدقيق |
| `entity_type` | TEXT CHECK | نوع السجل: حركة/سطر/مصروف/سحبية/قائمة/نظام |
| `entity_id` | TEXT | معرف السجل المتأثر |
| `parent_entity_id` | TEXT NULL | معرف حركة الربح الأم عند حدث السطر |
| `action` | TEXT CHECK | create/update/soft_delete/restore/activate/deactivate/import/backup_restore/database_move/reset |
| `before_json` | TEXT NULL | نسخة القيم قبل التغيير، JSON صالح |
| `after_json` | TEXT NULL | نسخة القيم بعد التغيير، JSON صالح |
| `occurred_at_utc` | TEXT | وقت الحدث UTC |

لا نستخدم triggers SQL لتوليد JSON؛ يجب أن تتم الكتابة من طبقة Repository داخل معاملة واحدة تجمع تعديل البيانات وسجل التدقيق. إذا فشل تسجيل التدقيق، تتراجع المعاملة المالية بكاملها.

### 3.8 `app_settings`

مفتاح نصي وقيمة JSON مع وقت التحديث. يحتوي الإعدادات التابعة للبيانات مثل رمز العملة واسمها ودقة العرض وعلامة وجود Demo في النسخة المستوردة. لا يحفظ مسار قاعدة البيانات هنا.

### 3.9 `schema_migrations`

رقم الترحيل، اسم الملف، SHA-256 لمحتوى SQL، ووقت تطبيقه. يمنع تشغيل تعديل قديم تغيّر محتواه بعد تطبيقه؛ كل تغيير بنيوي لاحق ينشأ ملف Migration جديد مثل `002_*.sql`.

### 3.10 `legacy_imports`

يحفظ بصمة SHA-256 للملف المستورد ونسخته الخارجية والداخلية ووقت الاستيراد. يمنع استيراد الملف ذاته مرتين، ويوثق مصدره.

## 4. Views والحسابات

| View | الغرض |
|---|---|
| `v_profit_transaction_totals` | حركة أرباح واحدة لكل رأس له سطر فعّال واحد على الأقل؛ count/quantity/amount مشتقة |
| `v_all_transactions` | اتحاد رؤوس الأرباح المجمعة والمصروفات والسحبيات لسجل العمليات |
| `v_daily_totals` | إجماليات اليوم، ومنها total_expense وnet، مع السحبيات مرة واحدة |
| `v_profit_by_item` | كمية وربح كل اسم صنف خلال التاريخ |
| `v_expense_by_category` | إجمالي المصروفات حسب التصنيف واسمه المحفوظ |
| `v_withdrawal_by_worker` | إجمالي السحبيات حسب العامل واسمه المحفوظ |

الحسابات بوحدة Integer:

```text
profit_milli          = SUM(profit movement amount_milli)
expense_milli         = SUM(expenses.amount_milli)
withdrawal_milli      = SUM(withdrawals.amount_milli)
total_expense_milli   = expense_milli + withdrawal_milli
net_milli             = profit_milli - total_expense_milli
```

لا يوجد عمود رصيد نقدية أو قيمة مبيعات أو تكلفة إنتاج.

## 5. الفهارس والقيود

- `PRIMARY KEY` لكل سجل.
- `FOREIGN KEY` لسطور الأرباح، المصروفات، السحبيات.
- `ON DELETE RESTRICT` حتى لا يسمح بالحذف المادي لسجل إدارة مرتبط بتاريخ مالي.
- `CHECK` للاسم غير الفارغ، الحالة 0/1، المبالغ والكميات موجبة، والقيم الرقمية ضمن مجال SQLite/JavaScript الآمن، وصحة JSON في سجل التدقيق والإعدادات.
- فهارس على التاريخ لدفتر اليوم والتقارير، وعلى `transaction_id` لسطور الأرباح، وعلى معرف العامل/التصنيف والتاريخ، وعلى حالة/اسم سجلات الإدارة، وعلى كيان/وقت سجل التغييرات.
- تفعيل `PRAGMA foreign_keys=ON`, `journal_mode=WAL`, `synchronous=FULL`, `busy_timeout=5000` عند فتح القاعدة.

## 6. معاملات الحفظ

### حركة ربح متعددة الأصناف

داخل Transaction واحدة:

1. إدخال صف `profit_transactions` واحد.
2. إدخال جميع السطور في `profit_lines`.
3. إدخال/تحديث كل أسماء الأصناف في `name_suggestions`.
4. إدخال حدث إنشاء في `audit_log` مع ملخص الحركة/السطور.
5. Commit. أي خطأ يؤدي Rollback ويمنع الحركة الجزئية.

### تعديل أو حذف صنف داخل الحركة

داخل Transaction واحدة: قراءة السطر النشط، حفظ `before_json`، تحديث الحقول أو `deleted_at`, حفظ `after_json`, تحديث اسم الاقتراح عند نجاح التغيير، ثم commit. لا يحتاج إعادة تخزين مجموع الرأس لأنه مشتق من View.

### المصروفات والسحبيات

داخل Transaction: قراءة التصنيف/العامل، تحقق النشاط عند الإنشاء، إدخال الحركة مع snapshot، ثم سجل التدقيق. لا تستخدم طبقة UI لتجميع السحبيات في جدول المصروفات.

## 7. ترحيل JSON الحالي

- الغلاف الخارجي المتوقع: `app='MowxBack'`, `schema=2`, `exportedAt`, `data`.
- بعد فحص `schema` الخارجي، يفحص المستورد `data.v` الداخلي (1 إلى 3). لا يخلط بين الرقمين.
- إذا كان `data.v` قديماً ولا يوجد `lines` لحركة ربح، يحول الحركة إلى سطر واحد بنفس معرف الحركة، ويولّد معرف سطر فقط لعدم وجود سطر تاريخي في المصدر.
- يسمح مستورد القيم التاريخية بثلاث منازل عشرية كحد داخلي (`amount_milli`) حتى لا يرفض تلقائياً قيمة قديمة أدخلها حقل `step="any"` حتى لو زادت عن دقة العملة المعتادة؛ القيم ذات أكثر من ثلاث منازل تُرفض برسالة بدلاً من تقريبها بصمت. إدخال/تعديل العمليات الجديدة يجب أن يتحقق من دقة العملة المختارة.
- لا يدمج الحركات القديمة.
- يحافظ على معرفات الحركة والقوائم والسجلات والخطوط المتاحة.
- يحافظ على `S.names` ويضيف أسماء خطوط الأرباح إذا لم تكن موجودة.
- يحافظ على سجل `S.log` مع تحويل `edit` إلى `update` و`delete` إلى `soft_delete`.
- الاستيراد مسموح فقط إلى قاعدة أعمال فارغة، معاملة واحدة. الملف الأصلي لا يمس. بعد استيراد ناجح تسجل بصمته لمنع التكرار.
- في حال فشل أي سجل أو مبلغ/تاريخ/مرجع FK، ترجع المعاملة كلها ولا تعتبر النسخة مستوردة.
- ملف ZIP الحالي لا يحتوي LocalStorage ولا JSON مستخدم، لذا لم يتم تنفيذ ترحيل بيانات حقيقية ولم يتم الادعاء بذلك.

## 8. النقل والنسخ الاحتياطي

### مسار قاعدة البيانات

- المسار محفوظ خارج DB في `%APPDATA%/MowxBack/mowxback-runtime.json` أو المسار الذي تعيده Electron `app.getPath('userData')`.
- عند أول تشغيل: يختار المستخدم مجلداً، ينشأ داخله `Data/mowxback.db`.
- إذا تعذر الوصول للمسار المسجل: لا ينشأ DB فارغ بصمت؛ يطلب البرنامج تحديد الملف الأصلي أو استعادة نسخة أو إغلاق البرنامج.
- النقل: يستخدم SQLite online backup API (`db.backup`) إلى ملف مؤقت في مجلد الوجهة، ثم `integrity_check`, `foreign_key_check`, وفحص بصمات محتوى الجداول والإعدادات والترحيلات والإجماليات، وبعدها فقط يحوّل المسار المعتمد. لا يستبدل DB موجوداً في الوجهة.
- تبقى القاعدة القديمة كما هي عند فشل النقل.

### النسخ الاحتياطي

- مجلد النسخ الاحتياطي إعداد منفصل في ملف إعداد التطبيق.
- `.db` backup كامل يؤخذ بـ`better-sqlite3` backup API، وليس نسخاً عشوائياً لملف مفتوح أثناء WAL.
- يُفحص ملف النسخة قبل اعتباره ناجحاً.
- الاستعادة تنشئ نسخة أمان من القاعدة الحالية وتتحقق من ملف المصدر قبل الاستبدال، ثم تفتح القاعدة المستعادة وتتحقق من سلامتها.
- يمكن نقل ملف النسخة إلى جهاز آخر ثم اختيارها من البرنامج.
- يمكن الاحتفاظ بمستورد JSON الإضافي، لكنه ليس بديلاً عن نسخة SQLite الكاملة.

## 9. ما لا ينفذه هذا التصميم

لا يوجد مخزون، أو مبيعات، أو أسعار بيع، أو تكاليف إنتاج، أو قيود مدين/دائن، أو صندوق، أو كشوف رواتب، أو رصيد راتب عامل، أو مزامنة أو حسابات مستخدمين. لا تحسب قاعدة البيانات هذه المجالات ولا تحتاجها الواجهة الحالية.


## دقة العملات

تُخزن المبالغ بوحدة الألف من العملة (`amount_milli`, scale=1000) حتى تدعم قاعدة واحدة العملات ذات منزلتين وثلاث منازل دون تغيير نوع العمود: SAR/AED/USD/EGP منزلتان، وJOD/KWD ثلاث منازل وفق وحدات ISO 4217 الفرعية. العملة المخصصة تستخدم منزلتين افتراضياً لأن نموذجها الحالي لا يطلب دقة مخصصة. تسجل الدقة في `app_settings.currencyDecimalPlaces` وتستخدمها طبقة التحويل والتحقق، ولا يغير تغيير العملة أي `amount_milli` محفوظ. عند الربط يجب أن يتغير منسق `fmtNum` الحالي (الذي يحد العرض بمنزلتين) كي لا يخفي المنزلة الثالثة في JOD/KWD. مرجع دقة الوحدات: [جدول رموز العملات والوحدات الفرعية](https://docs.reddragonpay.com/docs/Appendix/Currency-Codes-Units/)؛ والجهة الرسمية التي تدير قوائم ISO 4217 هي [SIX](https://www.six-group.com/en/products-services/financial-information/market-reference-data/data-standards.html).
