# تقرير تنفيذ المرحلة الثانية — ربط MowxBack بقاعدة SQLite

**تاريخ التنفيذ:** 23 نوفمبر 2026  
**الحزمة المرجعية:** `MowxBack-Database-Foundation.zip`  
**المخرج:** نسخة عمل محدثة لربط الواجهة بـSQLite من خلال Electron Main/Preload/IPC وRepository.  
**الحالة:** اكتمل تنفيذ الربط على مستوى الشيفرة واختبارات SQLite/Repository/عقد IPC. لم يكتمل إثبات التشغيل النهائي على Windows؛ لا يُعلن البرنامج إصداراً نهائياً معتمداً قبل الاختبارات المذكورة في قسم الحدود.

---

## 1. نطاق التنفيذ والمحافظة على المصدر

- فُحصت الحزمة المرفقة ومحتوياتها قبل التعديل، واستُخدم `reference/original-source/` كمرجع محفوظ.
- ملفات المصدر الأصلية لم تُعدّل داخل مجلد المرجع.
- بقي `css/main.css` دون تعديل في مرحلة الربط، ولم تُضف خطوط أو CDN أو موارد خارجية.
- حافظت الواجهة على اللغة العربية وRTL والصفحات والنوافذ ومسار الاستخدام الحالي؛ التغيير في مصدر البيانات والتنفيذ الخلفي، وليس إعادة تصميم.
- ملفات الواجهة في جذر المشروع أصبحت نسخة العمل المربوطة. لا تفتح `index.html` مباشرة في متصفح عادي لتشغيل قاعدة البيانات؛ يلزم تشغيل Electron.
- لم تُضف مبيعات أو مشتريات أو مخزون أو رواتب أو صناديق أو حسابات بنكية أو تسجيل دخول.

## 3. دورة البيانات والأمان

1. عند بدء تشغيل Electron يقرأ Main إعداد المسار من `mowxback-runtime.json` داخل مجلد Electron `userData`.
2. عند التشغيل الأول، يطلب نافذة اختيار مجلد Windows، ثم ينشئ `Data/mowxback.db` داخله.
3. إذا كان مسار قاعدة موجودة غير متاح أو كان الملف مفقوداً/فارغاً/تالفاً، لا يتم إنشاء قاعدة جديدة بصمت. يُطلب من المستخدم تحديد القاعدة الأصلية أو اختيار نسخة احتياطية أو الإغلاق.
4. تُحمّل الواجهة Snapshot من SQLite إلى متغير ذاكرة للعرض فقط. إعادة تشغيل التطبيق تعيد قراءة البيانات من قاعدة البيانات؛ لا توجد كتابة تشغيلية في localStorage.
5. كل عملية حفظ/تعديل/حذف تمر من Renderer إلى دالة مسماة في Preload ثم قناة IPC إلى Main ثم Repository.
6. العمليات متعددة الخطوات تنفذ داخل SQLite Transaction، وسجل التغيير يكتب ضمن المعاملة نفسها لضمان عدم تسجيل تحديث غير محفوظ أو العكس.
7. التقارير تُقرأ من استعلامات Repository/SQLite مباشرة؛ ليست مجرد تجميع من ذاكرة الواجهة.

إعداد BrowserWindow:

```js
contextIsolation: true,
nodeIntegration: false,
sandbox: true,
webSecurity: true
```

Preload لا يكشف `ipcRenderer` أو `fs` أو `require` ولا يوفر `invoke(channel, payload)` عامة. كما يتحقق Main من أن طلب IPC صادر من `webContents` والإطار الرئيسي للنافذة الموثوقة، ولا يستقبل SQL خاماً من الواجهة.

## 5. ربط الوظائف الحالية

### أرباح الأصناف

- الحفظ يتم كرأس حركة واحدة وسطور مرتبطة بها.
- يقبل سطراً واحداً مباشرة عند الضغط على الحفظ حتى دون إضافته أولاً إلى القائمة، كما يقبل عدة سطور في النافذة نفسها.
- تعديل السطر أو حذفه لا يؤثر على بقية السطور.
- إجمالي الحركة والكمية يستخرجان من السطور غير المحذوفة.
- حذف جميع السطور يجعل الحركة غير ظاهرة في الدفتر والتقارير، مع الاحتفاظ برأس الحركة والسطور المحذوفة وسجل التغيير.
- الاسم حر ولا يشترط وجوده في `items`.

### اقتراحات أسماء الأصناف

- المصدر جدول `name_suggestions` مستقل عن `items`.
- يُستدعى البحث من الواجهة بعد حرفين على الأقل.
- تطبيع الاسم يزيل المسافات الزائدة ويعالج اختلافات الأحرف العربية الشائعة في مفتاح المقارنة.
- Repository يضيف/يحدث الاسم داخل Transaction ناجحة لحفظ حركة الأرباح أو تعديل السطر.
- حذف الحركة أو السطر لا يمسح الاسم من سجل الاقتراحات.

### المصروفات والعمال والسحبيات

- المصروفات وسحبيات العمال لها عمليات إضافة وتعديل وحذف منطقي.
- تغيير اسم التصنيف/العامل لا يمحو الاسم التاريخي؛ تحفظ الحركة أيضاً لقطة الاسم (`category_name_snapshot` أو `worker_name_snapshot`).
- يمكن إيقاف وإعادة تفعيل سجلات الإدارة دون حذف الحركات السابقة.
- لا يوجد نظام رواتب أو رصيد مستحق للعامل.

### التقارير

- التقرير اليومي والشهري والفترة المحددة يرسل مدى التاريخ إلى Main.
- تُستخرج الأرباح والكميات والمصروفات والسحبيات والتجميعات والتفاصيل من SQL.
- المعادلة: صافي النتيجة = أرباح الأصناف − المصروفات.
- يحتسب SQL إجمالي المصروفات من نوعي `expense` و`withdrawal` مرة واحدة لكل نوع. السحبيات تظهر أيضاً كتفصيل مستقل لكنها لا تضاف مرتين.

### العملة

- الخيارات المعتمدة: SAR وJOD وAED وKWD وUSD وEGP وعملة مخصصة.
- تخزن المبالغ كعدد صحيح `amount_milli`؛ وتخزن الكميات `quantity_micros`.
- دقة العرض/الإدخال للعملات ذات 3 منازل (JOD/KWD) أو منزلتين لبقية العملات المدعومة، والعملة المخصصة افتراضها منزلتان.
- تغيير العملة لا يحول الأرقام التاريخية ولا يغير `amount_milli`؛ تم اختبار ذلك على Repository.

## 6. النسخ والنقل والاستيراد

### المسارات

- قاعدة البيانات في `Data/mowxback.db` خارج مجلد التثبيت.
- إعداد مسار القاعدة ومجلد النسخ الاحتياطي يخزن منفصلاً في `userData`.
- مجلد النسخ مستقل عن مجلد القاعدة.

### نسخ القاعدة ونقلها

- `lifecycle.js` يستخدم SQLite Backup API بدلاً من نسخ ملف DB المفتوح مباشرة.
- النقل يأخذ بصمة Hash وأعداد الصفوف والإجماليات، ينشئ نسخة مؤقتة ويفحصها ثم يقارنها قبل حفظ المسار الجديد.
- الاستعادة تفحص نسخة المصدر، تصنع نسخة أمان من القاعدة النشطة، ثم تبدل ملف القاعدة وتعيد فتحه وفحصه. عند فشل مسار الاستعادة تحاول إعادة ملف الأمان وفتح القاعدة الأصلية.
- هذه الطبقة لم تُختبر بعد مع `better-sqlite3` الأصلي على Windows.

### استيراد JSON القديم

- يتوقع المستورد الغلاف `app: "MowxBack"` و`schema: 2` ثم يتحقق منفصلاً من الإصدار الداخلي `data.v` (1 إلى 3).
- يدعم حركة الربح القديمة ذات الصنف الواحد بتحويلها إلى سطر واحد مع الحفاظ على معرف الحركة.
- ينقل المعرفات والأسماء والتواريخ والقيم والملاحظات والسجلات التاريخية المتاحة.
- يمنع استيراد نفس محتوى الملف مرتين عبر SHA-256.
- يشترط قاعدة أعمال فارغة ويجري الاستيراد في Transaction واحدة؛ أي فشل يؤدي إلى Rollback.
- لا يحذف ملف JSON القديم أو يعدله.
- ZIP لم يتضمن بيانات LocalStorage الخاصة بالمستخدم؛ لذلك اختبر المستورد ببيانات fixture فقط، ويجب تجربة ملف JSON الحقيقي قبل اعتماده.

### النسخ التلقائي

غير مفعّل في هذا الإصدار. لا يتم الادعاء بوجود نسخة يومية تلقائية.

## 7. منع بيانات Demo والتعديلات على الوظائف القديمة

- أزيلت مسارات بدء التشغيل التي كانت تستخدم `Store.seed()` أو `Store.migrate()` أو `localStorage`.
- لا ينتج غياب القاعدة أو خطأ تحميلها إلى حالة بديلة تحتوي بيانات تجريبية؛ يعرض التطبيق رسالة خطأ/استرداد واضحة.
- تم إخفاء زري «مسح البيانات التجريبية» و«إعادة ضبط» من واجهة التشغيل؛ لأنهما كانا يمسحان الحركات أو يعيدان بيانات Demo، ولأن الحذف الفعلي/إعادة ضبط مالية غير موجودة ضمن نطاق وظائف الدفتر المسموح بها. لم يُضف بديل يمحو بيانات الإنتاج.
- بقي استيراد JSON القديم وتصدير JSON ونسخ SQLite واستعادتها متاحة.
- لم يُضف XLSX حقيقي؛ زر التصدير لا يزال CSV، وزر PDF يمر عبر الطباعة. هذا نقص معروف لم يخفَ.

### ما الذي يثبته اختبار إعادة الفتح؟

تم إنشاء ملف SQLite حقيقي مؤقت باستخدام SQLite المدمجة في Node، وحُفظت فيه حركة، ثم أغلق الاتصال وأُعيد فتح الملف والتحقق من وجود المعرف والمبلغ وسلامة `integrity_check`. هذا يثبت ديمومة ملف SQLite في ذلك الاختبار، لكنه لا يثبت أن `better-sqlite3` native يعمل تحت Electron على Windows.

## 9. الاختبارات التي لم تُنفذ والقيود

1. لم يكتمل تثبيت npm dependencies في بيئة هذه المهمة؛ لا يوجد `node_modules` أو `package-lock.json` صادر عن تثبيت ناجح.
2. لم يتم تشغيل Electron Desktop فعلياً ولم يُختبر `better-sqlite3` مع Electron ABI.
3. لم يُشغّل Windows GitHub Actions ولم يُنتج ملف NSIS `.exe`، ولم يتم اختبار تشغيله على Windows مع فصل الإنترنت.
4. لم يتم تنفيذ اختبار UI end-to-end لكل النماذج والنوافذ داخل Chromium/Electron.
5. لم يُختبر اختيار مجلد Windows الأصلي، أو نقل DB بين أقراص، أو دورة النسخ/الاستعادة الكاملة باستخدام مكتبة `better-sqlite3` الفعلية.
6. لم يرفق المستخدم ملف JSON الحقيقي؛ اختبارات المستورد استخدمت Fixture فقط.
7. النسخ التلقائي اليومي غير مفعل.
8. تصدير Excel الحقيقي بصيغة XLSX غير منفذ؛ المتاح CSV فقط.
9. PDF يفتح نافذة الطباعة؛ لم يختبر حفظ PDF من Windows.
10. يجب تشغيل اختبارات `better-sqlite3` وElectron على Windows قبل اعتبار النسخة قابلة للاستخدام الإنتاجي.

## 10. طريقة التشغيل والبناء على Windows

من مجلد المشروع في PowerShell:

```powershell
npm install
npm run rebuild:native
npm test
npm start
```

لبناء مثبت:

```powershell
npm run dist:win
```

يستخدم `dist:win` Electron Builder بهدف NSIS x64، ويخرج الملف في `release/`. كما يحتوي `.github/workflows/build-windows.yml` على سير عمل Windows 2022، Node 24، تثبيت الحزم، إعادة بناء المكتبة، الاختبارات، والتغليف.

من الهاتف يمكن رفع التعديلات إلى GitHub وتشغيل Workflow من Actions. لا يُعد وجود Workflow دليلاً على نجاحه؛ يجب تشغيله فعلياً وفحص Artifact وتجربته على Windows.
